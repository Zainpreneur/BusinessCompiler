# Cross-Platform Data Aggregation & Advanced Analysis

Compiles `analytics.externalSources` and `analytics.crossSourceAnalyses`. This is the last
substantive section compiled in Stage 3 — deliberately, not by accident: it depends on
knowing every integration (`09-integrations-framework.md`) and everything exposed through the
platform API (`20-api-and-webhooks.md`), so it can only be written once those are settled.
Its output still files under the Intelligence cluster (`02-intelligence/data-aggregation.md`)
alongside `analytics.md`, since it's an analytics capability — only its *compilation order*
is last, not its place in the output structure.

`13-analytics-and-reporting.md` builds the reporting cube from the business's own BIR data.
That's necessary but not sufficient: a lot of the most useful analysis — true ad ROI, full-
funnel conversion, equipment downtime cost, partner/franchise benchmarking — requires data
that doesn't live in the BIR at all, because it's generated by a platform this business
merely connects to. This section is what pulls that data in and makes it analyzable
*together with* native data, not just alongside it in a separate, disconnected dashboard.

## The aggregation model

Treat every integration and every inbound platform-API partner as a **data source**, not just
a functional connector. For each one worth analyzing (not every integration needs this — a
calendar sync feeding availability doesn't need its own analytics ingestion), define an
`externalSources` entry:

- `integrationId`: the source (from `integrations`, or a named partner feeding data in
  through `platformApi`'s inbound webhooks — e.g. a franchisee's own POS pushing sales back).
- `contributes`: what it actually adds — be specific ("ad spend and impressions by campaign
  and day," not "marketing data").
- `joinsToDimensions`: which of `analytics.dimensions` (Time, Branch, Channel, etc.) this
  source's data keys against — this is what makes it *joinable* into the same reporting cube
  as native data rather than living in its own silo. A source that can't be keyed to a shared
  dimension can't actually be blended, only viewed side by side — say so if that's the case.
- `freshness`: external data almost always lags native data (a nightly ad-platform sync vs.
  a real-time `Order` write) — state the lag so nobody reads a same-day report assuming
  same-day ad spend is in it.

Mechanically, this is a periodic (or webhook-driven, where the source supports it) ingestion
job per source landing normalized rows into a warehouse/store keyed to the shared dimensions,
which `13-analytics-and-reporting.md`'s reporting cube then queries across — the same
`analytics.query` tool agents already use (`04-ai-agents.md`) should transparently span native
and external data once this is wired up, not require agents to know which source a number
came from.

## What each integration category typically contributes

Not exhaustive — compile what applies to this business's actual integration list:

- **Payments**: processing fees, chargebacks, payout timing — feeds *true* net margin (gross
  revenue minus what the processor actually takes, not the sticker price).
- **Accounting** (external): GL balances, if the business uses an external tool instead of
  the native ledger in `16-accounting-finance.md`.
- **E-commerce/POS**: channel-split revenue, online vs. in-store basket differences.
- **Maps/logistics**: actual delivery time and cost vs. estimated — feeds route/dispatch
  agent performance review.
- **Communications & WhatsApp**: delivery rate, read rate, response time — feeds marketing
  attribution (`08-marketing-crm.md`) with real engagement data instead of assuming every
  sent message was seen.
- **Web analytics** (GA/Pixel): traffic and on-site conversion funnel — feeds the top-of-
  funnel stages in `08-marketing-crm.md` that the BIR alone can't see (a visitor who never
  became an `Order` has no BIR record at all).
- **IoT telemetry** (`21-assets-equipment-iot.md`): sensor trend data — feeds both the
  predictive-maintenance agent and downtime-cost analysis.
- **Platform API inbound** (`20-api-and-webhooks.md`): whatever partners push in — most
  valuably, comparable data from multiple locations/franchisees, enabling cross-location
  benchmarking no single BIR instance could produce alone.

## Cross-source analyses (the payoff)

This is the actual "advanced analytics" — analysis that's impossible from any one source
alone. Define `crossSourceAnalyses` for whichever of these apply, naming the exact sources
combined and the question answered:

- **True blended ROAS**: ad spend from every connected ad platform ÷ revenue attributed to
  those campaigns via the promo-code/UTM tracking already defined in
  `08-marketing-crm.md` — answers "is paid marketing actually profitable," not just "what did
  the ad platform's own dashboard claim."
- **Full-funnel conversion**: web analytics traffic → BIR `Order`/`Appointment` creation →
  repeat purchase — answers where the business is actually losing prospective customers,
  spanning before-and-after the point where they enter the BIR at all.
- **Downtime cost**: IoT-flagged equipment failure/degradation windows × the revenue/capacity
  that asset represents (from `21-assets-equipment-iot.md`) — answers "what did that
  breakdown actually cost us," in dollars, not just hours.
- **Partner/franchise benchmarking**: platform-API data from multiple locations/franchisees
  compared on the same measures — answers "which locations are actually outperforming, and on
  what," which only exists once more than one external system is feeding in comparable data.
- **True cost-to-serve**: payment processing fees + delivery/logistics actuals + support
  ticket volume per customer/segment — answers which customers are actually profitable once
  the costs invisible to the BIR alone are included.

Each analysis should be feasible from the `externalSources` actually defined above — don't
list an analysis whose inputs weren't named as a source; that's the same "unbacked metric" gap
`22-qa-and-completeness.md` checks for, just at the aggregation layer instead of the BIR layer.

## Data quality and honesty

Blending sources of different freshness and reliability is where analytics quietly becomes
misleading if it isn't handled carefully:

- Surface each source's `freshness` on any dashboard/report that blends it with real-time
  native data, so "as of" is visible, not implied to be current.
- Degrade gracefully when a source sync fails — flag the report as partial, don't silently
  compute a blended number missing one of its inputs and present it as complete.
- A sync failure on a source feeding a cross-source analysis is exactly the kind of thing
  `05-automations-reminders.md`'s failure-handling pattern and `09-integrations-framework.md`'s
  retry/dead-letter logic should already cover — reuse it rather than inventing separate
  monitoring for analytics ingestion specifically.

## Output format

An external-sources table (integration/contributes/joins-to-dimensions/freshness), a
cross-source-analyses list (name/sources used/question answered), and a short data-quality
note. Right-size this: a business with one or two integrations gets a short paragraph noting
there isn't much to aggregate yet; a business with a real partner/franchise network or several
marketing/ad integrations gets the full treatment — this is where "advanced analytics"
actually earns the word.
